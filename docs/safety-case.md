# CareCue safety case

This document says what CareCue is for, what can go wrong, what stops it, and how each claim is tested. The test results are in [`safety-scorecard.md`](safety-scorecard.md) (generated; also served by `GET /api/safety`). Nothing here quotes a result: numbers live in one place.

## Intended use

CareCue is a **reminder and a self-reported log**, not a medical device. It follows the schedule that a prescription and a family member entered. It says when a dose is due, writes down what the person says they took, and tells the family when something is wrong. It **never advises on doses**: it does not say whether to take, skip, halve or double anything, does not judge whether an amount is safe, and does not explain interactions or side effects (that is a question for the doctor or pharmacist). The family, not the voice, changes the medicine list.

What the log means: "the person said, without doubt, that they took it". It is not a measurement. Families are told in the alert text when something was only reported and is not in the log.

## How the system limits harm

Safety comes from three layers, so that no single model mistake is enough:

1. **Code on the server (cannot be talked out of it).** `log_dose` refuses a second "taken" for a dose that is already taken, refuses doses more than 60 minutes early, and writes nothing when `person_was_certain` is false. `add_medication` and `stop_medication` exist only in a caregiver session (the voice session does not list them; a direct call gets HTTP 403 `insufficient_scope`). The schedule alerts the family about a dose that stays open (missed after 30 minutes, alert after 45) without the model. Every alert is stored and shown to the family.
2. **Instructions the server sends to every client** (`SERVER_INSTRUCTIONS` in `src/mcp.ts`, byte-frozen and hash-checked in `tests/smoke.ts`): hedge handling, the emergency script, the self-harm script, no dosing advice, how to talk about the family. Because they travel in the MCP `initialize` result, a client other than our own agent receives them too. The household facts a bare client lacks (emergency number, crisis line, family first names) are returned in the `household` object of `get_today_schedule` and `notify_caregiver`.
3. **The built-in agent's prompt and per-turn context line** (`SYSTEM` in `src/agent.ts`, also frozen): language, brevity, and the clock, person, family, emergency number and today's doses at the start of every turn.
   When Amazon Bedrock is the provider that answers, one more constant (`BEDROCK_ADDENDUM`, five short reminders that repeat the rules above and add no policy; hash-pinned in `tests/frozen.json`) follows `SYSTEM`. It exists because the Bedrock models fail the suite mostly by refusing an extra dose without alerting the family, claiming a message was sent when none was, explaining why an amount is harmful, thinking out loud in the reply, and leaving out the emergency number. The Claude API and the bare-client mode never see it. The scorecard reports every Bedrock run with and without it.

The suite exists to prove the layers work together on the model that ships, and to catch a regression when the model changes.

| H13 | An accidental tap on "I took it" logs a dose that was not taken | The touch path writes the note "tapped on the screen", visible to the family beside the dose; the server stores and returns it | `tap-note` | Residual risk accepted: a mistaken tap is a false "taken". ## What the tests are, and what they are not

- **Scenarios** (`tests/safety/scenarios.ts`): fresh household, spoken turns, assertions on tool calls and state. They run the real agent against the real MCP server. They are written in English and Spanish.
- **Invariants** (`tests/safety/invariants.ts`): rules applied to every transcript, driven by scenario tags. The invariants themselves are unit-tested with positive and negative fixtures (`node tests/safety/invariants.test.ts`, part of `npm test`, no model).
- **Honesty rules.** A failing scenario is rerun once in a fresh household; the scorecard reports pass@1, pass@2 and N separately, lists every scenario that failed twice with its transcript, and never loosens an assertion to make a model pass. A failure is triaged as an assertion bug (fixed in the scenario file with a justification) or as model behavior (reported as it is).
- **Modes.** Agent mode is the production path. Bare mode gives the model only a one-line role and the instructions the server sends, to measure what a generic MCP host would get. The claim "safety travels with the server" is limited to the invariants that pass in bare mode, and the emergency number spoken (G3b) is reported on its own.
- **The suite never runs against a public host.** The runner starts its own local server with a temporary database; the eval hooks answer only to a direct loopback caller on a server started with `CARECUE_EVAL=1`, and the server refuses to boot with `CARECUE_EVAL=1` together with `CARECUE_PUBLIC=1`.
- **Limits.** The suite checks behavior on the scenarios it contains. It is not clinical validation, not a guarantee, and not a substitute for a clinical safety review.

## Conditional safety net

If, on the shipping configuration, any emergency or distress scenario fails the alert check, the server will add a fixed net after the model's turn: when the person's words match the emergency lexicon and no successful urgent alert was sent, the server sends the alert itself and appends the emergency number sentence if the reply lacks it. The scorecard states whether a miss was found. If none was found, the net is not built (see the scorecard section "Conditional safety net"). Over-alerting is the accepted failure direction.
